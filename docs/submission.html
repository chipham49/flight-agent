The problem

Who it's for

A budget traveller who wants the real cheapest option in under a minute, with sources they can check.

What goes wrong today

Finding a cheap flight means checking several sites, then discovering bag fees and basic-economy limits late. That takes 30–60 minutes per trip, and the "cheapest" fare often isn't the cheapest once a suitcase is added.

Why an agent, not a script

Requests are messy ("from my usual airport to Seattle on Dec 20"), searching needs judgement across sources, and results must be checked and enriched with fee rules. Fixed code can't read free text or search pages, and an LLM can't be trusted alone with prices.

So the agent combines both: the LLM understands and searches, and plain code validates, prices and ranks.

Architecture

A fixed 7-step workflow over one shared state object (AgentState). Each step runs once, inside a tracing span.

  1. guard_inputRefuse booking, card numbers, injection, too long
  2. parseHaiku 5.5Free text → structured trip, dates resolved
  3. load_memorySaved preferences fill gaps; airport lookup; ask if unclear
  4. searchSonnet 5.5 + web searchCache first; prices validated by code
  5. enrichRAG: bag fee from the airline knowledge base
  6. rankDe-duplicate, sort by true total, keep 3
  7. respondTable, warnings, sources, output check
Design decisionWhy
Fixed workflow, not a free-roaming agentPredictable, testable and traceable; the LLM only does the parts that need judgement
Cheap model (Haiku) for parsing and extraction, stronger model (Sonnet) for web researchCuts cost on the simple steps
Prices validated by code, not by the LLMA price is kept only if its link came from the actual search results and its route, date and airline match. This blocks invented prices.
RAG for bag feesFee rules are long, change often and differ per airline; retrieval with citations beats putting them all in the prompt
Search only, never bookSafety and scope

2Agent Architecture & Orchestration

15 pts
  • An orchestrator runs 7 steps in order over one shared AgentState. Steps live in a single STEPS list.
  • Long-term memory: saved preferences (home airport, checked bags, max stops) fill gaps, such as "from my usual airport".
  • Clarifying questions when the origin, destination or date is missing (at most 2 rounds).
  • Hard limits, so no endless loops: 12 steps and 120 seconds per run, 1 search retry, 6 web searches per call, 3 pause continuations.
  • Any unexpected failure ends the run safely with a clear message, and the trace is still saved.
flight_agent/agent.py flight_agent/state.py flight_agent/store.py config.yaml

Not done: no agent framework (deliberately kept as plain Python), and no chat memory across conversations.

3Tooling & Integration

10 pts
  • Web search: Claude's server-side web search tool, capped per call, with source URLs and citations collected.
  • Airport lookup: a local table of about 80 airports, so city names resolve to codes (New York → JFK, LGA, EWR).
  • Bag-fee lookup: the RAG retriever (criterion 4).
  • Currency conversion to USD, and a search cache with a 30-minute lifetime.
  • Every tool call is recorded in the trace with its input, output, time and errors.
flight_agent/llm.py flight_agent/airports.py flight_agent/store.py

Not done: a paid flight-price API and an MCP server for the tools. Both are listed under next steps.

4Retrieval / Knowledge (RAG)

10 pts
  • A knowledge base of 11 notes: bag fees for 10 US airlines plus general travel rules, each with a source link and date.
  • Section chunking, query rewriting with synonyms, an airline metadata filter, BM25 ranking and top-3 results.
  • The answer cites the bag-fee source, and the true total is fare + bag fee × passengers.
  • The eval's bag-fee case went from 0% to 100% between v1 and v3.
knowledge/ flight_agent/rag/retriever.py

Not done: reranking with a model and multi-hop retrieval. The fee notes are based on 2025 policies and are not refreshed live.

6Evaluation & Testing

15 pts
  • A dataset of 15 cases in 6 groups (domestic, international, vague, bag fees, memory, guardrails). Dates are relative, so cases never go stale.
  • Automatic scoring of behaviour, route, results found, citations, disclaimer and bag fee applied.
  • Three live runs on the 8-case quick set: v1 75% → v2 88% → v3 100%. Each fix came from a failure the eval found and has its own test (see Eval results).
  • A comparison script with a regression gate: CI fails a pull request whose eval results are worse than v1.
  • 33 unit and workflow tests use a fake model, so they are free to run and run in GitHub Actions.
  • Eval cost is controlled: 3 web searches per search and no retry during evals, and a run stops at $1.50.

7Reliability & Guardrails

10 pts
  • Input: refuses booking and payment requests ("pay with my card"), card numbers, prompt injection, and over-long input. These refusals happen before any model call and cost $0. Off-topic questions are refused after parsing.
  • Trip checks: rejects past dates (a stated year is kept, so "January 5 2020" is refused instead of moved to 2027), dates more than about 11 months ahead, a return before departure, and more than 9 passengers.
  • Web text: lines in search results that look like instructions to the AI are removed before the agent uses them.
  • Offer validation: a price is dropped unless its link came from the search results and its route and date match. Offers without a named airline are dropped. Prices not quoted word-for-word get a "double-check" warning.
  • Fallbacks: retry with other sources → stale cache → an honest "no results" message. If the model declines, the API retries on a fallback model.
  • Output: every answer carries a disclaimer and a source link for every price.
flight_agent/guardrails.py 3-refused-past-date.json 4-refused-booking.json

8Performance & Cost

5 pts
  • Cost and time are measured on every run and printed with the answer.
  • Cache: the same LAX → New York search went from 27.1 s and $0.065 to 1.1 s and $0.0002.
  • The cheap model (Haiku 5.5) handles parsing and extraction, and the stronger model only handles search. Prompt caching covers the fixed search prompt.
  • Refusals and clarifying questions take about 1 second and cost at most $0.0002.

Run it

Setup

pip install -r requirements.txt
export FLIGHT_AGENT_API_KEY=your-key-here
python -m flight_agent --check-key

The key check is free: it only lists the models.

Use

python -m flight_agent "LAX to New York on December 15"
streamlit run app.py
python -m pytest -q
python -m evals.run_evals --version v4

The tests are free. An eval run costs about $0.20.

Limitations and next steps

Limitations

  • Prices come from web search, not a booking API, so results can be incomplete.
  • Many prices come from airline route pages ("from $179"), so times and stops are often unknown and prices are flagged "double-check".
  • Bag fees are based on 2025 policies and are not re-verified. Budget airlines price bags dynamically.
  • The airport list covers about 80 major airports, and currency rates are fixed approximations.

Next steps

  • A real flight-price API and flexible dates (±3 days)
  • Tools served through an MCP server
  • Hosted tracing (Langfuse) and a deployed web UI
  • An LLM-as-judge for answer quality, and more eval cases and repeat runs
  • Price-drop alerts and live refresh of the bag-fee knowledge base
